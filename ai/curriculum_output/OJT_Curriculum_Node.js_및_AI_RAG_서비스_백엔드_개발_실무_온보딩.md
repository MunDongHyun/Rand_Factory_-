# 📚 훈련실행 단계 (주차별/단계별 세부 훈련 지도안)

| 세부 훈련 목표 (역량 요소) | 핵심 OJT 학습 내용 (상세) | 활용 실무 자료 | 수행 실습 과제 (현업 적용형) | 멘토 피드백 포인트 (체크리스트) |
|---|---|---|---|---|
| 사내 API 서버 아키텍처를 이해하고, 요청 흐름과 책임 분리를 설명할 수 있다 | 멘토가 먼저 사내 API 서버의 레이어 구조를 함께 열어 보며 “라우터 → 컨트롤러 → 서비스 → 레포지토리 → DB” 흐름을 실제 요청 하나로 시연합니다. 그 다음 멘티에게는 각 레이어가 어떤 책임을 갖는지 단순 암기가 아니라, “이 로직이 컨트롤러에 있으면 왜 나쁜가?”, “서비스와 레포지토리를 분리하면 어떤 장애 대응이 쉬워지는가?”를 말로 설명하게 하여 구조 이해를 확인합니다. 마지막에는 장애 발생 시 로그를 어디서 먼저 확인하고, 어떤 레이어에서 원인을 좁혀가는지 실제 운영 관점으로 연결해 가르칩니다. | 사내 API 서버 아키텍처 다이어그램, 주요 모듈 소스코드, 운영 로그 예시, 장애 대응 Runbook | “사용자 프로필 조회 API” 하나를 지정하여, 멘티가 요청 유입부터 DB 조회, 응답 반환까지의 경로를 직접 추적하고, 각 레이어의 역할을 1페이지 요약 문서로 정리한 뒤 5분 발표로 설명합니다. 이어서 동일 API에 대해 “응답 지연이 발생한 경우 어디를 먼저 점검할지”를 기준으로 진단 순서를 작성합니다. | 1. 요청 흐름을 레이어별로 끊어서 설명했는지 확인합니다.<br>2. 책임이 맞지 않는 코드가 컨트롤러/서비스에 섞여 있지 않은지 확인합니다.<br>3. 장애 원인 파악 순서를 로그/쿼리/외부연동 순으로 실무적으로 제시했는지 확인합니다. |
| AI RAG 파이프라인을 기존 백엔드에 안전하게 연동하고, 검색-생성 흐름을 검증할 수 있다 | 멘토가 문서 수집, 청킹, 임베딩 생성, 벡터 검색, 재랭킹, LLM 응답 생성의 전체 흐름을 “그림”이 아니라 실제 운영 시나리오로 연결해 설명합니다. 예를 들어 “사용자가 환불 정책을 질문했을 때 어떤 문서가 검색되고, 어느 단계에서 근거 문장이 선택되며, 최종 응답에 어떻게 출처가 남는지”를 단계별로 보여줍니다. 멘티에게는 단순히 API를 호출하는 것이 아니라, 검색 결과가 왜 그 문장인지 검증하고, 검색 실패·오검색·환각 응답을 구분하는 판단 기준을 익히게 합니다. 또한 운영 관점에서 검색 품질이 떨어질 때 로그와 메트릭으로 어디를 조정해야 하는지 함께 점검합니다. | RAG 서비스 설계서, 문서 청킹 규칙 문서, 임베딩/벡터 검색 테스트 API, 프롬프트 템플릿, 검색 로그 샘플 | “사내 FAQ 3건”을 대상으로 문서 업로드부터 질의 응답까지 엔드투엔드로 실행하고, 각 질문에 대해 1) 검색된 근거 문장 2) 응답에 반영된 출처 3) 검색 실패 시 대체 응답을 포함한 테스트 리포트를 작성합니다. 이후 “유사하지만 다른 질문” 2건을 추가로 넣어 오검색 여부를 확인합니다. | 1. 검색된 근거가 질문 의도와 실제로 부합하는지 확인합니다.<br>2. 출처가 응답에 명확히 남도록 구현했는지 확인합니다.<br>3. 검색 실패 시 단정적으로 답하지 않고 안전한 fallback을 적용했는지 확인합니다. |
| MySQL 쿼리를 효율적으로 작성하고, 성능과 가독성을 함께 만족시키는 습관을 체득한다 | 멘토는 단순히 “인덱스가 중요하다” 수준이 아니라, 실제 느린 쿼리와 개선 후 쿼리를 나란히 보여주며 설명합니다. 멘티에게는 WHERE, JOIN, GROUP BY, ORDER BY의 조합이 어떤 실행 계획을 유발하는지 설명하게 하고, 불필요한 N+1 조회를 어디서 제거할지 스스로 찾게 합니다. 이후 쿼리 최적화 과정에서 EXPLAIN 결과를 읽는 법, 조건절 순서보다 인덱스 활용 여부가 중요한 이유, 대량 데이터에서 페이징 전략을 어떻게 바꿔야 하는지까지 실무 사례로 연결합니다. | MySQL 스키마, slow query log, EXPLAIN 결과 예시, DB 인덱스 설계 가이드, ORM 사용 규칙 | “최근 30일간 주문 조회 API”에 대해 현재 쿼리를 분석한 뒤, 실행시간을 줄이기 위한 개선안을 2안 이상 제시하고, 그중 1안을 실제로 적용해 전/후 성능 차이를 측정합니다. 반드시 EXPLAIN 결과와 함께 “왜 빨라졌는지”를 서술형으로 보고합니다. | 1. 불필요한 전체 테이블 스캔이 제거되었는지 확인합니다.<br>2. 조인 조건과 인덱스가 일치하는지 확인합니다.<br>3. 결과 정확도는 유지한 채 성능만 개선했는지 확인합니다. |
| 사내 Git 컨벤션과 코드 리뷰 예절을 지키며, 피드백을 건설적으로 수용하고 반영한다 | 멘토는 첫 주에 Git 브랜치 네이밍, 커밋 메시지 형식, PR 설명 작성법, 리뷰 요청 시 포함해야 할 정보까지 직접 예시로 보여줍니다. 이후 멘티가 작성한 커밋 메시지와 PR 본문을 실제 운영 기준으로 수정하게 하며, 리뷰 코멘트에 대해서는 “왜 지적됐는지”를 재진술한 뒤 반영하도록 지도합니다. 리뷰 세션에서는 방어적으로 답하지 않고, “지적하신 우려는 이러하며, 반영 계획은 이렇다”는 식으로 응답하는 스크립트까지 연습시킵니다. | 사내 Git 컨벤션 문서, PR 템플릿, 코드 리뷰 체크리스트, 과거 우수/미흡 리뷰 사례 | 기능 하나를 구현한 뒤, 브랜치 생성부터 커밋 3회 이상 분리, PR 작성, 리뷰 요청, 피드백 반영, 재리뷰까지 전 과정을 수행합니다. 이때 PR 설명에는 “변경 목적 / 영향 범위 / 테스트 방법 / 미해결 리스크”를 반드시 포함합니다. | 1. 브랜치명과 커밋 메시지가 사내 규칙을 정확히 따랐는지 확인합니다.<br>2. 리뷰 코멘트에 변명 없이 수용 태도로 응답했는지 확인합니다.<br>3. 피드백 반영 후 변경 이유를 다시 설명할 수 있는지 확인합니다. |

# 📝 S-OJT 교수·학습 흐름도 (학습 전이 극대화)

* **핵심 학습 지도 전략:**  
  멘토는 “설명 30%, 시연 30%, 질문 유도 20%, 즉시 실습 20%” 비율로 운영합니다. 처음부터 정답을 주기보다, 멘티가 스스로 사고 흐름을 말로 풀어내게 하여 메타인지와 문제 정의 능력을 키웁니다. 또한 AI RAG 영역에서는 결과를 맹신하지 않도록 “왜 이 답이 나왔는가?”와 “어떤 데이터가 빠졌는가?”를 반드시 함께 묻는 비판적 사고 코칭을 적용합니다. 협업 측면에서는 리뷰를 평가가 아니라 개선 대화로 다루며, 피드백을 받은 뒤에는 멘티가 반드시 “반영 계획”을 다시 말하게 해 학습 전이를 확인합니다.  

* **일정 흐름도 (주차별 Action Plan):**
  1. **(1단계 / Onboarding & Observe):**  
     멘토가 사내 API 서버의 핵심 엔드포인트 2~3개를 직접 열어 요청-응답-로그 확인 과정을 시연하고, 멘티는 이를 옆에서 지켜보며 “요청이 어디서 들어와서 어디서 끝나는지”, “장애 시 어디를 먼저 볼지”를 노트에 기록합니다. 이 단계에서는 코드를 많이 쓰게 하기보다, 아키텍처 지도와 실제 로그를 연결해 보는 데 집중합니다. 멘티는 매일 관찰한 내용 중 “이해한 부분 / 이해가 안 된 부분 / 다음 날 질문할 것”을 기록합니다.  
  2. **(2단계 / Practice & Feedback):**  
     멘티가 기능 단위 작업을 맡아 페어 프로그래밍으로 구현하고, 멘토는 옆에서 필요한 순간에만 개입합니다. 구현 후에는 주 2회 코드 리뷰 세션에서 Git 컨벤션, DB 쿼리, 에러 처리, 로그 구조, RAG 검색 근거를 항목별로 점검합니다. 피드백은 “수정 요구 → 이유 설명 → 재작성 → 재검토” 4단계로 돌려, 한 번의 리뷰가 실제 습관 교정으로 이어지도록 합니다.  
  3. **(3단계 / Perform & Evaluate):**  
     멘티가 단독으로 작은 기능을 설계·구현·테스트·배포 요청까지 수행하고, 멘토는 실제 운영 관점에서 최종 점검합니다. 최종 면담에서는 코드 품질뿐 아니라 커뮤니케이션, 피드백 수용 태도, 문서화 습관까지 포함해 평가하고, 다음 4주간의 보완 과제를 합의합니다. 평가 후에는 멘티가 혼자 반복 수행할 수 있는 체크리스트를 개인용 IDP로 정리합니다.
